# Working in this repository

- The user authorized pi-TUI capability parity with native host execution, no cpd-added tool approvals or sandbox restrictions, and `~/` as the default working directory. pi-durable remains the execution/transcript authority. Check the [parity inventory](docs/pi-durable-features.md#pi-tui-parity) for what is actually implemented; authorization is not completion. Legacy migration and public/LAN exposure remain separate.
- This repository is public. Keep provider credentials server-side; never commit secrets, machine-local paths, conversation data, logs or database files. Review staged changes and built client assets for accidental exposure.
- Keep changes visible live during development: use Vite+ HMR for the client and watch mode for the server, and give the User the active preview URL. Preserve the active session's data directory when moving worktrees; check for an active response before restarting its host. Inject credentials only into the server process.
- Before changing content, read [documentation conventions](docs/CONTRIBUTING.md). For product claims, consult [design direction](docs/design.md); for historical claims, consult [problem and learning](docs/problem-and-learning.md).
- Author changes on a branch in a separate worktree; leave the primary checkout untouched. Check for overlapping ownership before editing. This repository does not require CPD v0 dispatch machinery.
- Before parallel implementation, identify shared integration surfaces and real dependencies; assign an integration owner instead of letting every worker independently rewrite shared wiring. Separate worktrees do not establish independent delivery. Prefer isolated modules/tests and land enabling contracts before dependent integrations. See the [parallel-delivery lesson](docs/problem-and-learning.md#parallel-implementation-is-not-continuous-delivery).
- For the current open-PR backlog, follow the User's creation-order landing queue: reconcile and verify the next PR against current `main`, then advance after the User merges it. Do not repeatedly refresh all later PRs solely to keep them conflict-free. Attribute verification to the tested head/base; a later merge may invalidate it. This queue does not authorize merging or prohibit parallel isolated work.
- Follow the conventions' content/link review guidance and report actual evidence. Distinguish commit, PR, merge and deployment; creating a PR grants no merge authority.
