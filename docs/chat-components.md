# Chat capability mapping

Settled direction, updated 2026-11-17: **assistant-ui > shadcn; no custom visual components**. Use supplied assistant-ui elements throughout the application; shadcn fills only documented gaps. Official elements' internal shadcn dependencies are accepted, not alternative application designs. The [128-element review](assistant-ui-elements.md) records the full-catalogue pass and its evidence limits. The existing dark theme remains the default.

This mapping is scoped to [pi-durable 1.5.2](pi-durable-features.md). A visual element does not authorize a new runtime capability, tool or host integration.

## Architecture and vocabulary

- One assistant-ui external-store runtime per mounted `Chat`, supplied from validated Hono/SSE snapshots. pi-durable remains authoritative for transcript, execution, queues and persistence.
- The official registry `Thread` owns layout, viewport, messages, actions and runtime composer. `Chat` binds the external-store runtime. A narrow `ComposerFooter` slot and native TriggerPopoverRoot integrate supplied slash, queue, confirmation and state elements outside the input shell, not another nested composer/menu.
- Activities belong in ordered reasoning/tool/data parts and, where justified, native reasoning/tool groups or RunActivity. Do not preserve the old Message/Trace/Marker wrappers as a second abstraction layer.
- The application owns routes, conversation selection, dimensions and provider/transport integration. Each visited chat has an immutable React key and its own retained runtime; changing selection does not repurpose another chat's runtime.
- Each instance keeps its own draft, scroll and disclosure state. Read-only views disable native input/actions and omit commands. Nonvisual host context lives in `chat-host.ts`, avoiding a circular presentation import.
- No Assistant Cloud, local transcript database, localStorage draft persistence, Vercel AI SDK runtime or client-side model/tool execution is enabled.

## 1. Conversation and messages

| Capability             | assistant-ui composition                                         | Status/boundary                                                                                              |
| ---------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Transcript and scroll  | Official Thread and its supplied viewport/footer/scroll controls | Native bottom-following, user-scroll pause, centered reading surface and registered sticky composer          |
| Participant content    | Message Root and Parts                                           | Adopted; durable IDs and order retained, no automatic adjacent-assistant merging                             |
| Assistant text         | Thread's supplied MarkdownText element                           | Adopted: Markdown/GFM headings, lists, tables and fenced code with code-copy controls                        |
| User text              | MessagePart Text                                                 | Adopted: literal text, line breaks and indentation preserved                                                 |
| Message actions        | Thread's supplied action bar and More menu                       | Adopted Copy/Export; unsupported Refresh is omitted by runtime capability                                    |
| Streaming              | Source-backed transient render identity                          | Adopted for unambiguous task-to-entry handovers; ambiguous/missed boundaries use canonical rows              |
| Loading/empty          | Runtime state, skeleton and welcome composition                  | Adopted; initial loading is not an empty transcript                                                          |
| Earlier history/gaps   | Native Thread LoadEarlier and supplied ErrorState recovery       | SDK-owned 50-entry pages/merge, retained view resume and explicit gap recovery; no false whole-history claim |
| Acknowledgement/retry  | Admission-aware composer submission and transport notices        | Preserves original payload/ID after uncertain delivery, not answer-completion claims                         |
| Interrupted answer     | Incomplete status and typed interruption receipt                 | Cancellation, error and output limit remain distinct; Continue stays separate                                |
| Custom events/activity | Allowlisted text, omission and interruption parts                | Positioned omission receipts only; unknown custom entry data stays hidden                                    |
| Images/files/sources   | Image/File/Attachment/Source elements and part renderers         | PNG/JPEG uploads and saved user/tool images use scoped references; other file ingestion is not enabled       |

Markdown does not enable raw HTML or code execution. Markdown image elements are disallowed rather than fetching remote URLs. Links are not verified citations. Neither Shiki nor Prism, math, Mermaid, maps nor arbitrary generative UI execution is installed just because the catalogue offers it.

The native viewport uses bottom anchoring with automatic following, not top-turn anchoring and its reserved empty response area. Reading older content pauses following; native ScrollToBottom resumes it. Free layout space stays outside the measured footer inset, so it is not mistaken for content covered by the sticky composer. Message rows use actual layout heights rather than offscreen `content-visibility`/intrinsic-height placeholders, so collapsed reasoning/tool rows do not retain expanded-height gaps. This trades away that rendering optimization for accurate layout. Disclosures retain their supplied open/close behavior; completion alone is not an error. Routine Working/acknowledgement status pills are omitted; native Send/Stop carries that control state without adding/removing a footer row when a turn ends.

### Transcript identity and projection (Batch 2)

Batch 2 added optional canonical parts, outcomes, entry/task attribution, conversation identity, retained-window entry IDs and live generation metadata. Original entry/model/content indexes survive filtering. The native-tools increment projects validated tool calls, arguments and textual output alongside ordered text. Provider-supplied `thinking` text is now a native `reasoning` part; saved PNG/JPEG images project as coordinates rather than binary payloads. Signatures/encrypted metadata, other media, arbitrary custom entry data and provider diagnostics are not forwarded.

Reasoning uses the official [assistant-ui runtime composition](https://www.assistant-ui.com/elements/reasoning): Thread's GroupedParts, ReasoningRoot/Trigger/Content/Text and Markdown renderer, with the supplied `ghost` variant. It opens during reasoning streaming and collapses afterward unless the reader chose otherwise. Only actual provider text is rendered; empty reasoning produces no disclosure. No synthetic step titles, elapsed-time estimates or hidden-reasoning reconstruction is added. Older omission-only reasoning receipts render nothing, not a paused AgentStatus bar. ThinkingIndicator, loaders and typing indicators are transient activity feedback, ReasoningEffort is configuration, and GuardrailNotice requires an actual guardrail event; none substitutes for the reasoning trace.

SDK `aborted` is an interruption, `error` an error and `length` an incomplete output limit. Unknown/missing assistant stop reasons remain incomplete. A busy run is not necessarily a streaming assistant message: explicit `live: null` suppresses stale partial replay and false streaming on settled answers. Native Stop reflects an active run; no separate generic Working pill is rendered.

Render aliases are transient and separate from canonical durable IDs. A pure projector transfers the previous live row key only to exactly one new, known single-message SDK assistant entry attributed to the same task after the observed append boundary, while that boundary remains in the window or is its immediate predecessor. Task/attempt and append boundaries distinguish retries and reused attempts; no text-prefix or timestamp matching occurs. React layout effects commit the per-Chat cache. Canonical entry/part IDs remain separate metadata; future durable actions must not target render aliases.

Ambiguous multi-entry updates, another conversation/task, dropped boundaries and unattributed scheduler salvage fall back to canonical rows, not guesses. Tested success, Stop and model-error handovers retain the mounted row and Markdown part. Reconnect within the retained view keeps aliases; a full page load uses canonical history without browser persistence. Dropped rows lose their aliases. Paging preserves these evidence limits rather than treating loaded historical entries as a new live handover.

Strict wire validation rejects duplicate message/part identities and unknown wire part types. Rejected frames retain history/drafts, disable new actions and show a sanitized error. A later valid frame clears only that frame error, preserving uncertain-operation retries.

### Complete history access (Batch 3)

`src/server/history.ts` binds one transient SDK `ConversationTranscript` to each browser view. The SDK's `entries()`, `loadEarlier()`, `fillGap()` and `resume` window own page boundaries, deduplication, ordering and gap detection. Each read loads at most 50 entries; record IDs are bounds, not contiguous counts. Loaded entries remain in the view as the watched recent window advances. Full canonical projection is recomputed over the loaded entries, but tool-result pairing never crosses an unresolved gap.

Thread's supplied ghost LoadEarlier control binds to real `hasEarlier`/`onLoadEarlier`; its runtime manages loading state and its viewport handles prepends. Gap markers appear at their SDK boundaries using supplied ErrorState with actual Load missing messages/Retry callbacks, not fabricated assistant text. Markers have no durable message identity or copy/export actions. ErrorState's optional action/pending labels and disabled state describe history reads without changing its visual design.

The read-only `/api/history` operation accepts a validated view ID and optional gap bounds; it never submits a run. History loading/errors/retry are independent of mutation admission, drafts and uncertain-operation retry IDs. Revisions within a view epoch reject stale page responses; retired epochs and closed observers cannot overwrite a replacement view. There is no browser SDK mount, raw entry/document forwarding, history database or localStorage layer.

Disconnect stops the observer, not work. The cached SDK transcript resumes on reconnect and explicitly marks missing ranges. A detached view expires after 30 minutes. After host restart/cache loss, the browser's oldest-entry bound reconstructs one oldest page plus the latest window, with SDK gap markers for anything still missing. A full page refresh creates a new recent view; stored history remains pageable. A view UUID selects transient read state, not an authentication credential. History managers are scoped by SDK conversation.

An empty terminal SDK page ends paging without dropping retained rows. Failed reads retain visible history and expose a read retry; no provider request or delivery retry is implied.

### Finding loaded turns

The supplied ConversationMap rail groups loaded user turns with their following assistant entries, previews them and navigates within the containing viewport. Gap markers are excluded; no project/fork tree is implied. The rail is hidden on narrow screens. Find in loaded history opens supplied ConversationSearch, scanning only visible transcript text parts (not reasoning, tool arguments/output or unloaded entries). Enter/Shift+Enter and next/previous step with wraparound; zero hits are safe. Queries are bounded to 256 characters and 1,000 matches. Hit IDs carry real native message IDs and offsets, not inferred durable identities. Search/map state stays with each mounted chat. Paging and streaming recompute matches without submitting work.

### Saved-history search and logical export

Chat details offers a separate **Search or export saved history** inspector: this chat, explicitly chosen chats, or all catalog chats. Archived chats require explicit inclusion; deleted catalog chats cannot be selected or resolved. The server checks catalog membership before scanning and rechecks selected membership/archive state before returning results. Those checks and scans are not an atomic catalog snapshot, so a lifecycle change can still race the final response.

Read-only search and export use bounded, fork-aware SDK `entries()` pages, independently freezing an upper entry per chat. They do not freeze the entire session atomically, index a second database or submit a run. Saved user/assistant text includes visible history before reset/compaction; reasoning, tool payloads, images, provider diagnostics and arbitrary SDK documents are omitted. Fork-inherited history repeats per selected chat with its origin conversation identified. Search uses literal Unicode-aware matching independently within each original text part, never across parts or omitted content. Canonical conversation/entry/message IDs and original part indexes identify hits; UTF-16 offsets are relative to that part. The bounded before/after snippets come only from that part. Export preserves part boundaries. Search displays the entry ID; opening another chat does not jump to that entry.

Queries allow at most 256 Unicode code points and the inspector returns at most 100 matches; backend entry, chat and export-size limits can also cap reads. Results show complete/capped and per-chat boundaries, with partial results identified. Cancelling a read detaches the request/scan, not agent work; stale scope or chat responses are discarded. Logical JSON or Markdown downloads preserve selected text and history markers, **not** a full-fidelity transcript or restorable database backup. Treat downloads as private conversation data.

## 2. Composer and run controls

| Capability               | Composition                                                   | Semantics                                                                                                                                                            |
| ------------------------ | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Multiline draft          | Official Thread composer                                      | Draft belongs to assistant-ui; Enter submits, Shift+Enter inserts newline, IME is preserved                                                                          |
| Send now/follow-up/steer | Native Send; runtime ComposerSlashCommands and TriggerPopover | `/queue` and `/steer` dispatch the current draft using explicit durable modes; idle steering never becomes an ordinary send                                          |
| Durable queue            | Supplied controlled MessageQueue below the composer           | SDK inbox only; mode labels distinguish boundary steering from next-run follow-up, and held input is not claimed delivered                                           |
| Withdraw                 | MessageQueue per-item removal callback                        | Placement race reports already-placed/settled/not-found honestly                                                                                                     |
| Stop                     | Native Stop bound to host abort                               | Also withdraws queued inputs; queued reset writes survive                                                                                                            |
| Continue                 | `/continue` selection                                         | Starts a run without adding user text or consuming the draft; not checkpoint Resume or Regenerate                                                                    |
| Reset/handoff            | `/reset` → supplied shadcn AlertDialog and Textarea           | One explicit Reset context action, optional multiline handoff; initial focus is Cancel, modal focus is contained and Escape/Cancel restores the originating composer |
| Attachments              | Supplied Attachment adapter, picker, paste and Image          | PNG/JPEG only; server checks image model support and retains originals, including removed drafts                                                                     |

Steering is requested at an eligible boundary, not an immediate interruption. Continue eligibility comes from idle active model context ending in user content/tool results, with no queued reset, not the recent transcript window. Continue/reset admissions use request IDs for safe retry; reset uses the SDK's public reset-entry shape.

The input placeholder advertises `/`. Runtime `unstable_useSlashCommandAdapter` executes supplied callbacks on selection with `removeOnExecute: true`; selected command text is removed before the callback reads the remaining draft. Write a draft, then append `/queue` or `/steer` and select it, or insert a command before existing draft text. The picker supports native keyboard/ARIA behavior. It is not an argument parser. Availability follows committed host state; the host still validates admission. Raw reserved command names/prefixes are refused by native Send rather than becoming user messages after Escape or an eligibility change. Other slash text, such as paths not matching a reserved command prefix, remains ordinary input.

MessageQueue keeps the registry design but accepts host placement wording and an optional running row: durable queues need not have a current user prompt, steering is not next-run input, and failure can hold queued input. No native assistant-ui queue is populated or drained. These small semantic adaptations do not introduce a new visual queue design.

## 3. Agent activity, tools and tasks

Preferred elements: Reasoning, ToolFallback/ToolGroup, RunActivity, TerminalBlock, TaskCard and appropriate task/status disclosures. Preserve text/activity ordering and actual ownership. Use native GroupedParts only with supplied part data; never invent hidden reasoning, progress percentages, timings or tool results.

Native `read`, `write`, `edit`, `bash` and `powershell`, plus registered `grep`, `find` and `ls` adapters, execute through pi-durable and NodeExecutionEnv. Arguments, running output and settled textual results use the supplied ToolFallback and Thread's tool grouping. A nonvisual adapter maps SDK pending/running/complete/error/cancelled/unavailable state to truthful labels. No approval, Run now or unsafe tool-retry callback is supplied. PowerShell needs an installed host executable.

`grep` searches matching text lines with ripgrep regex/literal and case controls; `find` lists file paths matching a ripgrep glob, not shell-find predicates. Both require host `rg` and use argv execution without shell interpolation. `ls` lists immediate entries with the public SDK directory reader. Paths resolve against the actual conversation environment; absolute/parent paths and explicitly selected symlink roots are allowed. Discovered symlinks are not followed. Ripgrep's ignore/hidden rules apply, with an important exception: a matching positive glob can override hidden/ignore exclusions. Tool descriptions expose these semantics rather than claiming an exclusion is an access boundary.

Search results stream in traversal order, not globally sorted. Result/line/record and SDK output bounds are reported as truncation, not exhaustive output or a complete spill archive. A result limit does not impose a command deadline: ripgrep can continue scanning, and explicit Stop cancels through the SDK. No forced timeout or filesystem permission gate is added. These read-only tools are replay-safe, but replay may observe files changed since the earlier attempt; it is not a filesystem snapshot.

The host also installs `load_skill`; its actual calls and results use the same tool presentation. Per-request project guidance and skill metadata are host-only prompt resources, not fabricated transcript messages or a resource browser. See [discovery, limits and trust](../README.md#project-guidance-and-skills). User-selected templates and configured extension loading remain unimplemented.

### Structured agent questions

The host-registered `ask_user` tool requests semantic human input, not permission to use a tool. The supplied ElicitationForm appears in the Thread footer for actual pending questions; bounded text, single-choice and multi-choice fields are supported, with multi-choice options rendered as toggles. It does not implement MCP elicitation. The answer or explicit decline goes directly to a conversation-scoped durable question service, not the busy chat-input queue, and does not consume the composer draft. No form draft is promised across a page refresh.

Each request is tied to its conversation, owning task, question ID and revision. The first resolution wins atomically; an identical retry of the original identity, revision and normalized response succeeds without changing it, while conflicting or stale responses are rejected. After an uncertain delivery the form retains its values and permits the same retry, or an explicit state refresh before another response. The UI does not optimistically claim resolution. Polling runs only for the active connected chat; read failures leave visible state stale and disable answering. Disconnect or navigation is not a decline.

Stop aborts the owning execution and makes its unanswered question non-actionable; it does not record a decline. The retained question record stays pending and the pending projection reports cancellation before removing it from the polling index. Forks start with no actionable inherited questions; archived chats are read-only and deleted chats reject access. GET may initialize or clean up SDK question metadata but does not submit a run or call a provider. Polling reads a separate index of outstanding questions, not the retained answer history; no active questions are arbitrarily dropped. The retained retry/history document grows with questions and is not a paginated history API; creation and resolution still access it.

Known `pi.tool-result` entries attach to the preceding unmatched call with the same SDK call ID and tool name, in transcript order. Reused call IDs in later rounds do not overwrite earlier results. Result entry IDs remain metadata separate from call-part identity. If the originating call has left the window, render the result as its own authoritative row with unknown arguments, not attached to a guessed call. Live progress overlays only an unsettled call owned by the current generation task; a missing result is unavailable, not successful. Arbitrary result details/documents are ignored. Output is rendered as literal text, never executed as HTML/JS.

Code-mode disclosures show allowlisted nested call names, canonical IDs and actual states, under the matching parent call. Live slots are associated by the SDK parent task and call IDs; completed calls use the SDK code-mode receipt. Nested arguments, outputs and raw errors are not projected and are labeled unavailable. Missing receipts remain unavailable. A recorded spill is indicated without exposing its path; absence of a spill receipt does not prove output was never truncated.

Fresh composer `!` and `!!` commands run as foreground SDK tasks, not model tool calls; `!!` entries have no model contribution. A scoped status read supplies observed progress independently of the conversation watch. Supplied tool disclosures show the command and bounded combined stdout/stderr tail in callback arrival order; this is not an interactive terminal. Stop targets the actual shell task. Cancellation or restart may lose uncommitted output and cannot undo effects; an interrupted command is not rerun. Image attachments are rejected for direct shell input, and `\!` sends a literal leading exclamation mark.

Tool output/arguments can contain sensitive local data: they are intentionally visible to the local user and persisted by the SDK, unlike hidden provider diagnostics. Saved PNG/JPEG tool images use the requesting conversation's authorized SDK history and preserve text/image order; unsupported formats remain omission receipts. The [parity inventory](pi-durable-features.md#pi-tui-parity) records the remaining feature work; subagents/background/task inspectors are not implemented by this increment.

## 4. Context, configuration and usage

Chat details opens a supplied shadcn Dialog around assistant-ui CostMeter and selected SDK recovery states. Read-only `/api/chats/:chatId/accounting` reports conversation UsageDoc and whole-Harness usage, including SDK-recorded failed/aborted and compaction spend, independently of loaded transcript pages. The meter's scope label is explicitly **this chat**, not “this run”; session means all conversations in the saved SDK session, including archived/deleted catalog rows. Input includes cache reads/writes; reasoning is a subset of output and unknown reasoning remains absent. USD amounts are SDK reported/catalog estimates (zero can include unpriced catalog values), not an invoice or context occupancy. Snapshots can advance independently during a run.

Details polls only while open and active. It shows actual attempt/tool-round counts, retry or deferred-poll timestamps, after-run work and sanitized last-unanswered reasons; it never forwards provider error text or invents duration/progress. Stop is distinct from failure. Read errors retain visible values as stale and retry without admitting work or consuming drafts. This does not reintroduce a routine Working bar. The Dialog shell is justified because assistant-ui supplies no dedicated host-inspection container; the supplied AssistantModal contains another Thread and is not a data inspector.

Chat details composes supplied ModelSelector with its native search, keyboard selection and thinking radios. Choices come exclusively from server `Models.getAvailable()` and `getSupportedThinkingLevels()`, not a client catalogue. Availability means configured provider auth/catalog support, not proof that a remote account permits every request. Credentials/headers/base URLs never cross this projection. Unsupported effort/model/provider combinations are rejected server-side. The host's SDK prompt section supplies each request's configured provider/model from `agent.model`; it is configuration evidence, not independent verification of provider weights.

Selections are explicit per-chat SDK `configure()` writes. Reopen preserves model and thinking instead of reapplying the initial default; new independent chats still get the default. Settings affect subsequent provider requests, including later rounds of a busy conversation; a request already pinned retains its request configuration. The picker stages choices until Save and never submits/clears the chat draft. Atomic expected-selection comparison rejects stale saves; repeating an already-current assignment is a no-op, not a request or tool replay. Unconfirmed/conflicted saves require a read refresh before another selection. Archived/read-only views show saved configuration but omit editing. Auth installation/login, arbitrary provider endpoints and broader settings remain unimplemented.

The context inspector uses committed SDK `context()` to show active entry IDs/kinds/contribution counts, the head marker and model-message role counts, independently of loaded history. The newest 200 boundaries are displayed; counts cover the full active context. A separately labeled heuristic sums UTF-8 bytes of supported committed message content and divides by four, rounding up. It is not a tokenizer and becomes unknown for images or opaque reasoning/signatures. The selected model's catalog context window is shown when available, alongside the observation time; neither figure measures the assembled request. System prompt assembly, extension and resource sections, tool schemas, provider framing/transforms, queued and in-flight content, and output/reasoning reservations are excluded. The estimate does not guarantee the next request fits.

The newest durable assistant generation message found in a backward scan of at most 200 raw entries supplies a distinct previous-request usage observation, with its model and message timestamp (not a claimed request-start time). If the scan reaches its limit, the observation is unknown rather than absent; exhausting history without finding one is distinct. Cache counters remain separate, 1h cache writes and reasoning are identified as subsets, and missing reasoning stays unknown. All-zero SDK defaults cannot establish a provider report, so usage is unknown in that case. The request may precede a reset, compaction, model change, new entries or in-flight work; even without those changes it is not comparable to the committed heuristic or current occupancy. Each scan page and the context, agent and live reads are independently timed rather than an atomic assembled-request snapshot, so concurrent commits can change what is observed. Token occupancy and headroom remain explicitly unknown. ContextDisplay/ContextBreakdown are not used as a fabricated occupancy gauge; supplied Collapsible and AgentStatus present real boundaries/status instead.

Manual Compact context invokes SDK `compact()` with optional instructions and reports **task admission**, not completion or summary placement. SDK summarization can overlap work; a nonblocking summary write is placed immediately when idle, or at an eligible boundary when busy. Empty/no-cut compaction can finish without a new head. Saved transcript entries are not erased. Details projects actual manual/threshold/overflow compactions, blocking/attempt/retry state and sanitized failure identity; raw errors stay private. Automatic thresholds remain SDK defaults rather than a second browser policy. Stop aborts manual foreground compaction through the existing SDK abort; background compactions retain SDK ownership semantics.

Compaction writes have no SDK request-ID API and are never automatically retried. Unconfirmed admission disables that inspector's action and asks the reader to inspect state before deliberately trying again. This is not durable deduplication. Read-only archived views omit the action, and lifecycle checks refuse archive/delete while a compaction is active. The optional instructions field reuses supplied Textarea because assistant-ui has no compaction-instructions input.

Manual compaction and direct shell admission use a durable reservation to avoid starting both concurrently. If compaction admission throws or the host stops before recording the task identity, the reservation remains unresolved; the public `compact()` contract does not identify a generally safe class of such failures to clear automatically. After restarting, an explicit release is allowed only when no compaction is live and any known task is terminal. Release does not start another compaction or establish whether an unknown original ran.

## 5. Recovery and connection

Connection, failure, cancellation and completion remain distinct. SSE disconnect detaches observation, not work; reconnect does not submit another run. Retain visible history and editable draft while observation is unavailable.

AgentStatus shows actual connection/reset/notice/interruption/read-only states; routine admission/busy feedback uses native composer controls, and idle has no permanent Ready pill. ErrorState exposes Retry only for an actual original-operation callback. Do not adopt StoppedRun/ConnectionState defaults with unwired actions or unobserved server-progress claims. No request-ID-safe retry is offered for uncertain Stop, because a later abort could stop newer work.

Diagnostics, detailed task recovery, compaction failure detail and custom document inspection require sanitized host projections. Raw provider errors, paths and credentials stay private.

## 6. Adjacent integrations

ApprovalCard, PermissionGrant, OptionList/QuestionFlow and ReviewableDiff require durable host protocols, actual evidence and authorization. ElicitationForm is used for [structured agent questions](#structured-agent-questions), not reset or MCP elicitation. General approval protocols remain unavailable.

### Chat navigation and creation

TanStack Router routes `/` to `/chats`, then selects the original active chat, or another active chat if the original is archived/deleted. Direct links, reload and back/forward select the same durable conversation. Unknown/deleted chats show supplied ErrorState rather than falling back silently. ThreadListSidebar and ThreadList come from the official assistant-ui registry, including their shadcn Sidebar/Sheet dependencies. Header/footer branding is application-specific. Supplied per-chat overflow menus support ellipsis, right-click and Shift+F10; Archive/Delete and archived-chat Restore bind real SDK catalog operations. Native inline Rename binds the durable catalog title, with Enter/blur commit and Escape cancellation; errors retain the input. Titles are trimmed, nonempty and at most 80 characters, and stale expected-title writes are rejected. Search filters active catalog titles only; no fabricated date groups or whole-transcript search. Running icons use polled SDK LiveDoc state, not a second background execution runtime. AssistantSidebar is an app/copilot split and is intentionally not composed as a second Thread.

`src/server/chats.ts` stores only catalog metadata in a session-scoped SDK document: original-chat adoption, titles, creation request IDs and lifecycle state. Creation, ownerless SDK conversation configuration and catalog registration share one SDK transaction. New chat reuses an active unnamed conversation only if it has no SDK entries, run or queued work. Distinct creation request IDs resolve to the same empty conversation; their mappings survive first-input naming and reopen. First admitted input supplies the title atomically with submission. Opening an older catalog archives extra empty active conversations without deleting their records. Restoring an archived empty chat is rejected while another empty chat is active. Unsent browser drafts do not become durable history and are not cleared by reselecting the empty chat.

`POST /api/chats/:chatId/manage` applies archive, unarchive or delete atomically. Running chats and chats with queued work/compaction must be stopped/resolved first; these actions never implicitly abort work. Archive moves the row under Archived chats, retains drafts and allows read-only transcript/history access; Restore re-enables input. Delete requires supplied AlertDialog confirmation and discards the visited runtime/draft, hides the catalog row permanently and rejects its endpoints. Deletion is a durable catalog tombstone, **not physical transcript erasure**: pi-durable 1.5.2 has no public conversation-purge API, so underlying records remain in storage. Reopen does not readopt a deleted original chat. Last-chat deletion leaves New chat available. The catalog is not a transcript database; projects and orchestration remain unimplemented.

Committed user/assistant message actions offer **Fork from saved entry**, using canonical `source.entryId`, never a transient render alias or inferred text position. A supplied AlertDialog confirms inheritance through the entire entry inclusively (including any additional model messages in that entry). Streaming/unknown-source/gap rows have no fork action. `/api/chats/:chatId/fork` atomically calls SDK `tx.forkConversation()` and registers catalog metadata plus request-ID mapping. The SDK verifies fork-aware visible history; foreign/missing IDs are rejected. A retry with the same identity/boundary returns the same saved fork; mismatched boundaries or archived/deleted results are rejected rather than recreated.

Forks are independent ownerless durable conversations: SDK history/configuration are inherited at the cutoff, not copied from the parent's newest configuration. Live tasks, queued input, unsent drafts and later history are not inherited. Forking neither regenerates a response nor replays tools; it does not stop the source. Each fork has a fresh SDK provider identity and starts execution only through its own controls. Ancestor history remains accessible after deleting a parent's catalog row because SDK storage is not purged.

The supplied standalone MessageBranches stepper navigates actual catalog conversation IDs in the selected lineage (root plus regular descendants), not assistant-ui's local message-branch store. Its labels say saved branches, and its message body is hidden using the documented stepper-only composition. The header exposes immediate source/cutoff and Open source chat when that source remains available. Sidebar/deep links also select each saved branch. Nested forks preserve their root lineage; archived branches stay in Archived chats, and deleting a source does not delete descendants. This is lineage navigation, not a project/task tree. Source/fork drafts and scroll remain separate; an acknowledgement arriving after the user navigated elsewhere does not force navigation back.

`GET/POST /api/chats` list/create chats. `/api/chats/:chatId/{input,control,withdraw,stop,history,events}` scope every operation and history cache to that conversation; legacy `/api/*` conversation endpoints still target the original. IDs are validated and resolved only from the catalog. The navigation-only assistant-ui runtime binds real create/switch callbacks; each visited Chat has a separate immutable native composer/runtime and transport. Hidden chats detach SSE, not SDK execution. Re-selection reconnects the retained history view; drafts, pending admissions and original retry identities stay with their chat until refresh. Outgoing reset dialogs close on route changes. Visited chats remain mounted for the workspace lifetime, so memory grows with visited/loaded history; no eviction or browser draft persistence is claimed.

## Current embedding contract

`src/client/chat.tsx` exports `Chat` and `ChatProps`. Supply title, optional description, validated presentation state (`null` during initial load), connection and pending/error/notice state. The parent supplies a bounded height. `src/client/chat-page.tsx` owns per-chat integration; `src/client/use-chat.ts` owns the immutable conversation-scoped API connection. Optional `active` closes transient reset UI when the containing workspace hides the chat.

Omit `onSend` for read-only mode. Otherwise it receives text, optional send mode and image reference IDs, returning true only for confirmed admission. `onStop`, `onContinue`, `onReset` and `onWithdraw` are optional host callbacks. `state.controls` gates advanced controls.

Optional `onLoadEarlier`/`onFillGap` bind history reads, with separate `historyLoading`, `historyGap`, `historyError` and `onRetryHistory`. Read-only embeddings may still page if their host supplies these callbacks. Without a paging adapter, the earlier-history notice remains informational.

Native composer Send reaches the external-store `onNew` host adapter. Because native Send detaches its draft eagerly, the adapter restores text and the same immutable image references if the composer is still empty. Confirmed admission clears only the unchanged text, ordered references and edit generation. Busy-mode slash commands use the same admission function without detachment. This preserves server authority without a second React draft store or an optimistic transcript. Drafts and retry identities are not persisted across refresh.

PNG/JPEG uploads are limited to four per input, 5 MiB each, 8,192 pixels per dimension and 32 million pixels. The SDK decoder prepares model content within 2,000×2,000 pixels and 4,500,000 base64 bytes; original bytes remain in the owner-only data directory and may retain metadata. Removed, failed-binding and otherwise unreferenced uploads are not automatically deleted. Pending references are conversation-scoped and do not become actionable fork drafts; inherited saved images resolve through the requesting fork's SDK history. Before request fingerprints existed, identical legacy retries cannot be verified and return 409.

After uncertain input/control delivery, the host supplies `uncertain`, an error and `onRetry`, with `retryText` or `retryAction`. Retain the original operation/payload/request ID. Other mutations stay blocked while a new draft remains editable. Continue/reset/withdraw do not consume the composer draft. Reset handoff text survives a failed attempt.

The transport serializes mutations and keeps retry identity only until refresh. Inspect restored state before repeating an uncertain action after refresh. Model Stop is a current-scope abort; shell Stop targets its identified task. An uncertain Stop asks for state inspection before explicitly stopping again.

## Remaining work

Source-backed live/committed identity, paged history/gap recovery, loaded-turn navigation/search, scoped saved-history search/export and ordered text/reasoning/tool/image/omission projection retain the limits above. Other media renderers, richer tool-specific result displays and application custom-event schemas remain unimplemented. The [catalogue review](assistant-ui-elements.md) distinguishes presentation candidates from host capabilities.

## shadcn gap decisions

**Reset and chat-deletion confirmation use supplied shadcn AlertDialog.** assistant-ui supplies no dedicated context-reset confirmation dialog, and ThreadList's native Delete action does not confirm removal/discarding an unsent draft. ElicitationForm adds server/plug identity, “needs input,” an extra confirmation field and Send/Decline semantics; it is not an appropriate destructive-action modal. Use the existing supplied shadcn **AlertDialog** for accessible modal confirmation and **Textarea** for optional reset handoff. These provide Cancel / Reset context or Cancel / Delete chat without another card, checkbox or custom visual component. Deletion starts focus on Cancel and explicitly distinguishes app removal from underlying record erasure. Reset focus starts on Cancel, stays in the modal, and returns to the correct composer. Cancel/Escape changes no server state and retains handoff text; Reset context alone admits the existing operation. Failure retains the handoff and the original request-ID-safe retry; admission does not mean the reset has been placed.

**Saved-history scope and export format use supplied shadcn Select and Checkbox.** assistant-ui's ModelSelector and SettingsPanel are model/configuration surfaces, while OptionList and ElicitationForm represent committed answers or agent questions rather than repeatedly editable local search options. None supplies the needed reusable scope, format and multi-chat selection semantics. The official base-nova controls fill that gap without a custom visual control or model/tool-question protocol.

The rest of Batch 1 remains assistant-ui-first: runtime ComposerSlashCommands/TriggerPopover, controlled MessageQueue, AgentStatus and ErrorState. Internal shadcn dependencies are accepted separately from this explicit fallback. No general dialog framework or new host capability is introduced. Future gaps must name the missing behavior and justify a specific supplied shadcn element or defer.
